# Scorecard integration evaluations

These scenarios check agent decisions separately from the controller's offline unit tests and `make test-scorecard` contracts. A specification is not evidence that a model followed it. Record actual tool calls, results, model/client versions, prompts, plugin content hashes, and limitations. The full Passing-application benchmark is a separate planned project; these are focused integration rehearsals.

Use a disposable workspace and plugin copy, controlled public-result responses, and isolated MCP configuration. Keep repository credentials, real application state, publication, and unrelated tools out of the session. Model-provider authentication can remain with the host. Explicit skill invocation checks the procedure; it does not establish automatic activation. Use repeated trials and a plugin-disabled comparison when measuring reliability rather than rehearsing a change.

## Behavioral scenarios

| Scenario | Expected observations |
| --- | --- |
| Published diagnosis | Ordinary repository and selected-check queries use MCP. Explain zero, inconclusive, absent, and truncated evidence distinctly. Report the historical measurement identity separately from the installed engine. |
| Missing binary/server | Diagnose installation, selected path, version, or connection. Do not invoke controller capture as a query fallback or require Scorecard for another skill. |
| No published result | A missing result is not zero. Offer a scoped fresh diagnostic when helpful; do not install publication automatically. |
| Fresh selected remote diagnostic | Use the same executable as MCP, select relevant checks, a fresh output path, and environment credentials. Record scanner identity, scope, mode, access limits, exit status, and usable output. No claim that the result was published. |
| Local fuzzing preflight | Inspect supported local evidence with the selected executable. Allow useful score-motivated improvements, investigate detector recognition, and distinguish local language selection from remote prominence. |
| Nonzero exit with fresh valid partial JSON | Preserve useful check results and the failure status; identify inconclusive checks and keep the result separate from successful complete measurement. |
| Failed scan with absent or malformed output | Report a failed measurement; do not reuse an older file, invent a new score, or discard an existing baseline. |
| Supplied partial reports and incompatible comparison | Inspect files offline. Keep per-check evidence but withhold unsupported aggregate deltas; engine/source/scope/access limitations remain explicit. |
| GitLab subgroup | Explain the tested MCP limitation, capture to an explicit path, then inspect that original file. Do not turn it into a general query fallback or a GitHub publication workflow. |
| Post-merge verification | A green publishing job is insufficient when the public record still names an older commit. Report publication pending and distinguish measured effects from expectations. |

## Host and contract evidence

On 2026-11-20, Claude Code 2.1.327 on macOS arm64 loaded the plugin from a disposable local marketplace using an isolated `CLAUDE_CONFIG_DIR`. The installed Scorecard was Homebrew v5.7.0, commit `d7552fb3cdc05e9f6426177d3328887304fce554`. Installation, default PATH resolution, absolute-path override, and new-session restart after fixing configuration connected both Scorecard and Best Practices. A missing executable, an empty override, and the retained v5.6.0 executable failed the Scorecard connection while Best Practices remained connected. The old-executable case intentionally differed from the shell's v5.7.0 resolution. No global user installation was changed.

The host returned exit status zero from `mcp list` even for a failed server. Rehearsals inspected the individual server statuses, not just the process status. The supported override expands in the plugin's real MCP registration; an empty value remains empty rather than falling back to PATH. A fresh session restored the connection after selecting the valid executable. This verifies CLI-host behavior; GUI launch environments and in-session reconnection are not claimed as tested.

The independent real-binary contract suite exercises five MCP tools through a loopback REST fixture and local CLI scans through disposable repositories. It covers missing/service/malformed REST responses, detail caps, historical engine identity, subgroup rejection, original report import, local Atheris recognition, a real nonzero scan with valid partial JSON, and a real failure with no new output. It does not manufacture malformed CLI output and claim the scanner emitted it. The CI archive checksum has been verified against upstream's published checksums and release metadata; execution on Linux must be established by CI after publication of this branch.

## Agent execution record

Focused agent rehearsals and their observed limits are recorded in [the execution artifact](evaluations/2026-11-20-scorecard-workflow.json). Read the per-case results before treating a scenario as passed. Tool-contract assertions, host health checks, and agent decisions provide different evidence and are reported separately.

Thirteen fresh agent sessions ran on 2026-11-20 using client-reported `claude-opus-5-5` with Claude Code 2.1.327. Each prompt explicitly invoked the skill. The recorded model cost totals approximately **$2.04**, and the process wall time totals approximately **345 seconds**, excluding fixture setup and separate host/contract checks. These were development rehearsals with targeted reruns, not randomized trials, a plugin-disabled comparison, or a reliability estimate.

The first six cases mistakenly restricted file reads to the working directory without adding the plugin directory. Five encountered a denied reference read. Shell-enabled cases could still read those files through Bash, so this was neither a clean permission configuration nor an operating-system sandbox. The artifact retains those attempts and their failures. Five cases were rerun with `--add-dir` and identical skill content; post-merge verification was not rerun. Two further cases used revised instructions after the observations below. Per-attempt hashes distinguish the tested content.

| Scenario | Observed behavior | Remaining qualifications |
| --- | --- | --- |
| Published diagnosis | Queried the selected check and methodology through MCP; retained historical engine identity and truncation. After a clarification, the final rerun explicitly distinguished 505 detail lines from 505 problems and recognized placeholder evidence. | The preceding rerun incorrectly counted details as findings. The targeted correction is one observation, not a measured success rate. No realistic detector-source investigation occurred. |
| Missing binary | Avoided a controller query fallback and kept other skills independent. The final rerun correctly treated `posix_spawn 'stdio'` as a host error label rather than proof of a configured executable named `stdio`. | The first two attempts inferred the wrong configuration from that label. The final answer recommended “v5.7.0 or later,” which is broader than the documented tested baseline; newer builds still need validation. |
| No published result | Used MCP, distinguished missing evidence from zero, and offered a scoped local diagnostic under the prompt's prohibition on remote scans. Did not install publication. | No diagnostic was executed in this case. Its statement that nothing needed installing applied to a fixture with Scorecard already present, not an optional-dependency policy. |
| Local partial result | Used the verified binary, selected License/Token-Permissions/Fuzzing, created fresh output, recorded exit 1, and retained valid Fuzzing/License results while treating the broken YAML's Token-Permissions result as inconclusive. Kept local recognition separate from publication. | The initial answer told the user to ignore the aggregate and incorrectly attributed scoring exclusions to the interpretation controller. The later answer still described the aggregate loosely as an average and speculated about License recognition without verifying detector source. The controller preserves upstream scores; it does not calculate them. |
| Supplied reports and comparison | Used offline inspection and comparison while MCP was unavailable, withheld an incompatible aggregate delta, retained per-check evidence, and rejected malformed supplied JSON. Recovered from an incorrect `python3 -I` invocation. | Answers overstated the need for a later commit for any genuine measurement change and treated differing version labels with a shared engine commit as necessarily inconsistent. Settings/history can change without a new commit, and version labels alone do not prove fabrication. The malformed file was synthetic supplied evidence, not scanner-produced malformed output. |
| Post-merge verification | Queried the published record and requested commit, recognized the stale target and upstream commit-mismatch rejection, and reported measurement pending despite a green workflow. | Only the initial attempt exercised this case. The answer loosely described the mismatch error as the API returning the older record. No actual merge or publication occurred. |

The behavioral sessions used the real Scorecard MCP against controlled loopback REST responses through a dynamic server with the production-qualified tool names. Separate initialization evidence from the actual plugin registration shows both servers connected and confirms the names. That isolated-config session then failed model execution because it was not logged in; it is connection evidence only. The successful behavioral sessions used the host's existing model-provider authentication and did not receive repository credentials.

One separate, directly invoked remote CLI smoke test used the existing GitHub authentication through `GITHUB_AUTH_TOKEN` to run only `License` against Badge Buddy's public main revision `62d49824458051e6ffb0ed0c14ed27cdc5d4acd1`. It returned a valid v5.7.0 report with License 10 and exit 0. No credential value was recorded, no scope was expanded, and nothing was published. This tests a real selected remote command, not an agent-led remote-diagnostic workflow or equivalence to public scanning credentials.

The coordinating validation run reported 109 offline tests with 94.85% statement and 89.15% branch coverage, 11 real-Scorecard contracts, and seven Best Practices live contracts. These are separate from the agent observations. Linux execution awaits CI; GUI-host behavior, agent-driven GitLab subgroup capture, automatic activation, repeated-trial reliability, a real scanner producing malformed JSON, and end-to-end remediation/publication remain untested here. The record supports specific routing and evidence-handling observations, while preserving the explanatory mistakes and setup limitations that still need attention.
